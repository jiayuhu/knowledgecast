# 任务页内容生产流程需求草案

本文从 `~/x/ideas/PRJ_20260504_KnowledgeCast/content-production-flow.md` 转译而来，面向研发需求讨论。本文只定义产品目标、MVP 边界和页面能力，不进入字段、数据库、API 或状态机实现细节。

相关设计补充：`docs/superpowers/specs/2026-05-08-planning-card-and-content-qa-design.md` 定义“培训策划卡”和“内容 QA 门”，用于细化骨架确认后进入创作、发布前判断内容可用性的产品边界。

## 背景

当前 KnowledgeCast 已具备素材采集、AI 整理、培训页生成、私密分享和版本历史等基础能力，但产品体验仍偏向“材料采集 -> AI 生成”的线性流程。

企业内部培训场景下，用户真正需要的是围绕一个培训任务持续推进内容：先明确任务，再采集材料，整理结构，分段创作，发布可用版本，并在反馈或新材料出现后继续迭代。

因此下一阶段需要把任务页建设为核心工作台，而不是把采集、整理、发布视为松散页面。

## 产品目标

任务页承载从采集、整理、创作到发布迭代的最小闭环。

目标不是做一个完整文档编辑器，也不是做泛知识管理工具，而是让用户能在一个培训任务中完成：

1. 围绕任务收集材料
2. 从材料整理出可讲结构
3. 基于结构分段生成和编辑内容
4. 发布当前可用版本
5. 为下一轮迭代保留入口

## 信息架构

产品信息架构分为三层：

1. 业务归属层：工作区、工作集等稳定导航结构，继续按业务属性划分
2. 内容任务层：一份要推进的培训内容，是材料、骨架、成稿、版本和反馈的核心容器
3. 生命周期层：任务当前处于采集、整理、创作、可用或迭代等阶段

业务归属层用于导航，生命周期层用于任务状态、视图重心和下一步动作，不作为 Sidebar 的主要组织方式。

## 命名与路由迁移

当前代码和文档中存在一个概念错位：`/workspace/[id]` 实际承载的是 Collection 级页面，而不是 Area / Workspace 级页面。

任务页重构时，建议逐步让 URL 与数据概念对齐：

1. 第一阶段不新增独立 Task 数据对象
2. 让现有 Collection 承担“培训任务 / 内容任务”的角色
3. 新路由建议采用 `/collections/[id]`
4. 现有 `/workspace/[id]` 及其子路由保留 redirect，避免旧入口失效
5. 新代码优先使用 Collection / Training Task 语义，老代码逐步迁移

建议迁移映射：

1. `/workspace/[id]` -> `/collections/[id]`
2. `/workspace/[id]/capture` -> `/collections/[id]/capture`
3. `/workspace/[id]/structure` -> `/collections/[id]/structure`
4. `/workspace/[id]/publish` -> `/collections/[id]/publish`
5. `/workspace/[id]/settings` -> `/collections/[id]/settings`

中文产品文案可以逐步从“工作集”过渡到“培训任务”或“内容任务”。数据对象第一阶段仍可沿用 Collection，避免把本轮工作扩大为对象模型重构。

后续只有在一个 Collection 需要承载多个独立培训任务时，才考虑引入独立 Task 对象。届时再讨论 `/collections/[collectionId]/tasks/[taskId]` 或 `/tasks/[id]`。

## 任务页定位

任务页不是培训页详情页，也不是材料文件夹。它是状态驱动的内容生产工作台。

任务页的核心原则：

1. 状态决定主工作区
2. 结构提供连续性
3. 上下文提供可信度
4. 下一步动作推动流转

## 任务页布局

任务页应保持四个稳定区域：

1. 顶部状态区：展示任务归属、当前阶段、当前可用版本和下一步动作
2. 左侧结构区：在整理阶段展示主线和骨架，在创作阶段展示骨架导航，在发布阶段展示版本结构
3. 中央工作区：承载当前阶段的核心工作，包括采集、整理、创作、发布或迭代
4. 右侧上下文区：跟随中央当前对象变化，展示依据、缺口、反馈、风险、新材料和 AI 动作

具体视觉设计和组件拆分后续在设计或实现阶段确定。

## MVP 流程

MVP 应优先打通以下流程：

1. 创建或进入一个内容任务
2. 任务接收材料
3. 系统基于材料生成内容骨架和缺口提示
4. 用户确认或调整骨架
5. 用户围绕骨架分段生成内容
6. 用户生成当前可用版本
7. 可用版本保留下一轮迭代入口

这条流程的核心验证目标是：KnowledgeCast 不再只是材料采集工具，而能帮助用户把材料推进到可讲内容。

## 阶段需求

### 草稿 / 采集阶段

目标：让任务获得足够的材料基础。

页面应突出：

1. 材料进入当前任务
2. 当前材料是否足以开始整理
3. 当前内容还缺什么
4. 开始整理的入口

采集阶段不以材料库为中心，而以当前培训任务为中心。

### 整理阶段

目标：把材料变成可讲的结构。

整理阶段是 MVP 的关键差异化，应支持：

1. 生成或展示内容主线
2. 生成可编辑的内容骨架
3. 显示骨架部分背后的材料依据
4. 暴露内容缺口
5. 支持用户确认结构后进入创作

整理阶段不应只展示摘要、聚类或材料分类。核心交付物是用户认可的内容骨架。

### 创作阶段

目标：把结构变成可用表达。

创作阶段应围绕骨架分段推进，而不是优先生成完整长文。

MVP 应支持：

1. 选择骨架中的一个部分
2. 查看该部分的依据和缺口
3. 生成当前部分的内容草稿
4. 对当前部分进行改写或补强
5. 标记当前部分可用
6. 在关键部分完成后生成当前可用版本

### 可用 / 发布阶段

目标：把当前内容封为可用版本。

MVP 应表达“当前可用版本”的概念，避免把发布理解为永久完成。

页面应支持：

1. 查看当前可用版本
2. 使用或分享当前版本
3. 保留进入下一轮迭代的入口

复杂版本差异、培训使用记录和完整反馈治理可以后置。

### 迭代阶段

目标：让新材料、反馈或业务变化能推动下一版内容。

MVP 可以先提供轻量入口，表达当前版本可以进入下一轮，不要求完成复杂反馈闭环。

后续可扩展为：

1. 基于反馈回到采集
2. 基于反馈回到整理
3. 基于反馈回到创作
4. 基于旧版本复用为新任务

## MVP 优先级

建议优先级：

1. 任务页基础框架和阶段表达
2. 任务内材料进入和整理入口
3. 骨架生成和缺口提示
4. 围绕骨架的分段创作
5. 当前可用版本
6. 轻量迭代入口

## 后置能力

以下能力不建议进入第一版任务页 MVP：

1. 复杂反馈治理
2. 复用为新任务的完整流程
3. 复杂版本差异对比
4. 审批、权限和口径确认流
5. 完整文档编辑器
6. 多人协作编辑
7. 复杂字段建模和状态机配置

## 非目标

本阶段明确不做：

1. 不把 Sidebar 改成按生命周期组织
2. 不把任务页做成单纯材料列表页
3. 不把任务页做成 AI 对话页
4. 不把创作阶段做成完整长文编辑器
5. 不以一键生成完整培训页作为主路径
6. 不在本文定义数据库字段、API 参数或状态枚举
7. 第一阶段不新增独立 Task 数据对象
8. 不一次性全量重命名现有代码里的 workspace / collection / training 概念

## 验证标准

MVP 是否有效，可以用以下问题判断：

1. 用户是否能从一个培训任务开始，而不是从上传材料开始
2. 用户是否能看到材料如何转成内容骨架
3. 用户是否能知道当前内容缺什么
4. 用户是否能围绕骨架逐段生成内容
5. 用户是否能生成一个当前可用版本
6. 用户是否能理解这个版本未来还可以继续迭代

如果这些问题成立，任务页就完成了从材料采集工具到内容生产工作台的关键转变。
