# KnowledgeCast 设计稿

## 1. 目标

KnowledgeCast 是一个面向个人用户的小型 SaaS。它帮助用户把碎片化知识沉淀为结构化内容，并自动生成一个可分享的内部培训网页，用网页替代传统 PPT 来传播知识。

首版的核心验证目标不是“做一个完整知识库”，而是验证以下闭环是否成立：

`碎片输入 -> AI 整理 -> 结构化沉淀 -> 生成培训网页 -> 私密分享`

## 2. MVP 范围

### 2.1 包含

- 文字录入
- 语音转文字录入
- 链接导入
- 简单文本或 Markdown 文件上传
- AI 自动去重、聚类、提炼要点、生成大纲
- AI 追问补全信息
- 生成内部培训网页
- 轻量编辑生成结果
- 私密链接分享
- 邮箱验证码登录
- 草稿、已整理、已生成、已分享状态管理
- 简单搜索

### 2.2 不包含

- 复杂文档上传
- 协作编辑
- 多人实时编辑
- 内容商店或公开内容市场
- 复杂 CMS 能力
- 原始 HTML 源文件下载
- PDF 导出
- 公开匿名访问

## 3. 产品定位

KnowledgeCast 的定位不是泛知识管理工具，也不是全能内容平台。它只解决一个明确场景：

用户先把零散知识输入系统，系统再把这些碎片整理成能讲、能发、能传播的培训内容资产。

因此，产品的价值点有三个：

- 降低知识沉淀成本
- 降低培训内容制作成本
- 降低内容分发和更新成本

## 4. 用户与场景

### 4.1 用户

- 个人用户

### 4.2 受众

- 内部团队

首版默认只做内部培训场景。对外宣讲和客户展示可以作为后续扩展方向，但不进入 MVP 核心路径。

## 5. 访问与保护策略

用户明确要求三点：

- 不允许直接下载 HTML 源文件
- 不允许轻易复制全文
- 需要访问控制

### 5.1 选择的访问模型

首版采用 `私密链接 + 邮箱验证码`。

流程如下：

1. 创建者生成一个分享链接
2. 访问者打开链接
3. 系统要求输入邮箱
4. 系统发送一次性验证码
5. 验证通过后，短时间内可访问页面

### 5.2 保护边界

系统只保证“提高批量获取成本”和“限制无授权访问”，不承诺绝对防复制。

具体措施：

- 不提供 HTML 源文件下载
- 页面内容通过受控接口或服务端渲染输出
- 分享链接可失效、可撤销
- 页面加入访问者标识水印
- 对复制行为做轻量阻断，例如禁用部分快捷复制体验
- 对接口做鉴权和限流

### 5.3 明确不做的事

- 不把“禁止复制”当成安全边界
- 不做重型 DRM
- 不做复杂设备绑定
- 不做客户端源码混淆作为主要防护手段

## 6. 信息架构

### 6.1 输入层

负责收集碎片知识，支持：

- 纯文本
- 语音转写文本
- URL 链接
- Markdown 或纯文本文件

### 6.2 AI 整理层

负责把碎片内容变成结构化知识：

- 去重
- 聚类
- 提炼要点
- 生成大纲
- 追问补全

### 6.3 输出层

负责把结构化内容渲染成内部培训网页：

- 标题
- 章节
- 重点摘要
- 说明内容
- 总结

### 6.4 传播层

负责控制分享和访问：

- 私密分享链接
- 邮箱验证码登录
- 链接失效
- 访问记录

## 7. 交互流程

### 7.1 创建内容

1. 用户录入文字、语音或链接
2. 系统创建一个草稿
3. AI 分析并整理输入内容
4. 系统给出结构化大纲和补充问题
5. 用户进行轻量编辑
6. 用户生成内部培训网页

### 7.2 分享内容

1. 用户生成私密分享链接
2. 系统对访问者做邮箱验证码校验
3. 访问者进入页面阅读
4. 页面显示访问标识水印
5. 用户可随时撤销链接

## 8. 编辑策略

首版只做轻量编辑，不做完整在线文档编辑器。

允许编辑的内容：

- 标题
- 章节顺序
- 段落文本
- 小范围措辞调整

不允许首版覆盖的内容：

- 类 Word 的复杂排版
- 拖拽式任意布局
- 实时协作编辑

这样做的原因是：首版目标是验证内容从“碎片”到“可传播页面”的转换效率，而不是验证富文本编辑器能力。

## 9. 数据模型

### 9.1 核心实体

- `KnowledgeItem`：单条碎片输入
- `KnowledgeDraft`：整理中的知识草稿
- `KnowledgeOutline`：AI 生成的大纲
- `TrainingPage`：最终生成的培训页面
- `ShareLink`：分享链接和权限状态
- `AccessToken`：一次访问或短期访问凭证
- `AuditLog`：访问记录和操作记录

数据库层的表名和列名统一使用 `snake_case`；应用代码中的类型名和变量名保持 `camelCase` / `PascalCase`。

### 9.2 状态流转

`KnowledgeItem -> KnowledgeDraft -> KnowledgeOutline -> TrainingPage -> ShareLink`

状态建议：

- `draft`
- `processing`
- `needs_review`
- `ready`
- `shared`
- `revoked`

## 10. 系统架构

### 10.1 推荐架构

采用标准 SaaS 单体架构：

- 前端负责录入、编辑、阅读
- 后端负责鉴权、AI 编排、内容存储、分享控制
- 数据库层采用 `Drizzle ORM + SQLite`
- 数据库保存结构化内容和访问状态
- 对象存储可用于简单文件上传

数据库命名约定：

- 表名使用 `snake_case`
- 列名使用 `snake_case`
- TypeScript 层保持自然命名，不为了数据库强行改写业务代码

### 10.2 为什么选这个架构

- 对 MVP 足够
- 开发和部署简单
- 权限控制更直接
- 后续可以平滑拆分服务

### 10.3 不采用的方案

- 纯静态页面发布
- 过早拆成微服务
- 先做复杂内容工作流引擎

## 11. AI 设计原则

AI 只承担“辅助整理”，不承担最终真值判断。

设计原则：

- AI 先输出结构，再让用户确认
- AI 生成的大纲必须可编辑
- AI 追问只补足结构缺口，不无限扩写
- AI 输出要稳定、短、可复用

## 12. 安全与风险

### 12.1 主要风险

- 访问者仍然可以手工复制阅读到的内容
- 截图无法彻底禁止
- 共享链接可能被转发
- AI 生成内容可能不准确

### 12.2 处理方式

- 将“防批量下载”作为目标，而不是“绝对防泄露”
- 用访问控制、过期机制、水印和审计记录提高滥用成本
- 把 AI 输出标记为可编辑草稿
- 通过确认流程减少错误传播

## 13. 成功标准

MVP 成功的判定不是用户量，而是这条链路是否被验证：

- 用户能快速录入碎片知识
- AI 能把碎片整理成可读结构
- 用户愿意把结果发给别人看
- 分享页能被内部团队正常阅读
- 用户觉得它比手工做 PPT 更省时间

## 14. 后续演进

验证 MVP 后，优先演进的方向是：

- 提高 AI 整理质量
- 丰富培训页模板
- 提升访问保护能力
- 增加团队级权限
- 再考虑 APP 作为高频输入端

## 15. 结论

KnowledgeCast 的核心不是“记录知识”，而是把知识变成可传播、可复用的内容资产。

首版应该坚持：

- Web 优先
- 私密访问
- 轻量编辑
- 内部培训场景优先
- 防源文件下载，但不追求不现实的绝对防拷贝
